# 公式資格と基礎知識資格の出題割合をランダムにする

- 状態: 完了（dev 反映・検証済み 2026-10-05。prod は人間の確認待ち）
- 起票日: 2026-10-05

## なぜやるか

MLA などの公式資格は、基礎知識資格（ML）の問題を混ぜて演習できる（`includeCompanion`、specs/003）。
この混ざる割合が**ランダムではなく、構造で固定**されていて、公式が優先されて見える。

本番 API（ゲスト条件・30回試行）で実測した結果、試行ごとのばらつきはゼロだった:

| 公式 + 基礎知識 | 先頭5問の基礎知識 | 先頭10問以降 | プール全体の基礎知識の比率 |
|---|---|---|---|
| MLA + ML | **20%**（公式4:基礎1） | **60%** | 35% |
| AIF + ML | **0%**（公式5:基礎0） | 50% | 40% |
| DEA + DB | 20% | 60% | 27% |
| SCS + SEC | **0%** | 40% | 32% |

原因は2つ:

1. **フィルタなし**: 公式と基礎知識の全問を1つの `domainBalancedOrder` に渡している。
   deficit round-robin が**バケット（ドメイン）の数**で割り振るので、割合はドメイン数の比で決まる
   （MLA 4 : ML 6 → 基礎60%）。しかも、同数のときは並び順で決まり、公式が先に並ぶ。
   そのため短いセッションでは公式が優先され（AIF の5問は基礎知識0）、長くなると逆に
   プールの比率より基礎知識が多くなる。
2. **フィルタあり**（未回答・不正解・ブックマーク）: 各スコア階層の中で、公式を全部出し切ってから
   基礎知識を出す（specs/004）。

## 何を作るか

公式資格の通常演習で基礎知識資格が混ざるとき、**1問ごとに「公式／基礎知識」を、残りの問題数に
比例した確率でランダムに決める**。

- 期待される基礎知識の割合は、プール（または階層）の問題数比と一致する
  （例: MLA は公式314問・基礎166問なので、平均 約35%）
- どちらが先に出るかも毎回ランダム。短いセッション（5問）でも偏らない
- **フィルタ（未回答・不正解・ブックマーク）をつけたときも同じ**ランダム混在にする。
  specs/004 の「公式を先に使い切ってから基礎知識で埋める」は**廃止**する。
  各スコア階層（フィルタ一致度）の中で、その階層の問題数比に比例して混ぜる
- 各側（公式・基礎知識）の内部では、これまでどおりドメイン均等化（deficit round-robin）を維持する

## 受入条件

- [ ] フィルタなしで MLA（`includeCompanion=true`）の先頭10問を多数回取得すると、基礎知識の割合の
      平均がプールの比率（約35%）に一致し、試行ごとにばらつく（固定60%ではなくなる）
- [ ] 先頭5問でも基礎知識が0問〜複数問の範囲でばらつく。AIF・SCS でも基礎知識が出る
- [ ] 公式側・基礎知識側それぞれの並びは、ドメイン均等化の順序を保つ（相対順序が変わらない）
- [ ] フィルタ（例: 不正解を優先）をつけても、同じ階層の中で公式と基礎知識が混ざる
      （公式を使い切るまで基礎知識が出ない、という挙動がなくなる）
- [ ] 階層の順序（フィルタ一致度の高い階層が先）は維持される
- [ ] 対応する基礎知識資格が無い資格（SAA など）は、出題順序が従来と変わらない
- [ ] 模試（`includeCompanion` を渡さない）は影響を受けない
- [ ] 全問が出力に1回ずつ含まれる（落ちる・重複する問題がない）

## 対象外（やらないこと）

- 基礎知識の割合の設定値・上限キャップ（今回は問題数比のみ。設定が欲しくなったら別spec）
- 件数表示の内訳（specs/004 の項目2。本specでは触れない）
- ドメイン別統計・予想スコアへの基礎知識分の算入（既存方針を維持）
- フロントの大きな変更（サクッと演習・演習は出題順をサーバが返す `questionIds` で決めるため API の変更だけで足りる）。
  ただし**しっかり対策だけはフロントで抽出する**ため、`Home.tsx` の「フィルタ時に公式を先に抽出」分岐を除去した
- フォールバック経路 `src/utils/domainBalance.ts`（`getPrefetch*` が常に null で到達しない。
  docs/06 の既存の注記のとおり、復活させるときに同じ変更が要る）

## 影響範囲

| 種別 | 影響 |
|---|---|
| 画面 | なし（サーバが返す出題順だけが変わる） |
| API | `GET /questions?idsOnly=true` の並び順（`includeCompanion` 付きのときだけ） |
| DynamoDB | スキーマ変更なし |
| 夜間バッチ | 影響なし |
| デプロイ | **Lambda を dev+prod に反映**。フロントは `Home.tsx`（しっかり対策の抽出）の分岐除去のみ |

## 既存の不変条件との整合

- 出題プールの条件 `!isHidden && !!validityCheckedAt` を維持するか: **はい**（プールの決定には触れない）
- ドメイン均等化（deficit round-robin）の方針に反しないか: **反しない**。CLAUDE.md の確定方針
  「無フィルタの通常演習のドメイン配分は deficit round-robin を維持する」は、
  **各側（公式・基礎知識）の内部で維持する**。変わるのは、2つの側をどう混ぜるかだけ。
  「1セッション内で特定ドメインが多くなる/0問になるのは許容」も変わらない
- ゲスト/ログイン境界に反しないか: 反しない（新機能の開放なし）
- `correctAnswerIndices` を正準とする不変条件に触れるか: 触れない
- specs/004 との関係: 項目1（出題優先順位）を**置き換える**。項目2（件数表示）は影響を受けない。
  specs/004 の「対象外」に「将来『常に一定割合を基礎知識に回す』ニーズが出たら別specで」と
  あり、本specがそれに当たる
