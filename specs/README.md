# specs/ — 仕様駆動開発

**このディレクトリは「これから作るもの」を置く。** 現状の仕様は `docs/`。

## なぜ仕様駆動にするか

このプロジェクトはバイブコーディングで育ってきたため、
「なぜそうなっているか」がコードの外に残っていない箇所が多い。
結果、次のような事故が起きた。

- ドメイン均等化を prod Lambda へ反映し忘れ、1か月ランダム出題が続いた
- 検証(02)の「体裁は無視する」という方針が、自動改良によって崩されかけた
- ゲスト機能の境界が曖昧になり、ローカル累積データが不整合を起こした

**先に「何を・なぜ」を短く書いてから実装する**ことで、
実装が意図から逸れたときに気づけるようにする。

## ディレクトリ構成

```
specs/
├── README.md              ← このファイル
├── TEMPLATE/              ← コピー元
│   ├── spec.md            What / Why（要件）
│   ├── plan.md            How（設計）
│   └── tasks.md           実装タスク
└── NNN-機能名/            ← 実際の機能。NNN は連番3桁
    ├── spec.md
    ├── plan.md
    └── tasks.md
```

## 使い方

### 1. spec を切る

```bash
cp -r specs/TEMPLATE specs/001-focused-mode-filter
```

`spec.md` を埋める。**実装方法は書かない。** ここで書くのは:
- 誰の何の困りごとを解決するのか
- 完成の判定条件（受入条件）
- 対象外（やらないこと）

### 2. plan を書く

`plan.md` に設計を書く。ここで初めてファイル名・テーブル・API が出てくる。
**必ず `docs/` の該当箇所を読んでから書く**（既存の不変条件を壊さないため）。

### 3. tasks に分解して実装する

`tasks.md` にチェックリスト形式で並べ、上から実装する。

### 4. 完了したら `docs/` へ反映する

**これを飛ばすと `docs/` が腐って archive/ の二の舞になる。**
実装した内容を `docs/` の該当ファイルへ反映し、`spec.md` の先頭に完了日を書く。

## 判断に迷ったときに参照する順序

1. `docs/website-manifest.txt` — 作者の制作意図（最上位）
2. `CLAUDE.md` — 確定済みの開発ルール（デプロイ手順・デザイン規約・ゲスト境界）
3. `docs/` — 現状の実装仕様
4. `specs/` の既存 spec — 過去の判断とその理由

## spec を切らなくてよいもの

以下は spec 不要。直接実装してよい。

- 誤字・表記の修正
- 明らかなバグ修正（意図した挙動が分かっているもの）
- スタイル調整（デザイントークンの範囲内）
- ドキュメントの更新
- 夜間バッチのパラメータ調整

**spec を切るべきもの**: 新しい画面・新しいAPI・データモデルの変更・
出題や採点のロジック変更・ゲスト/ログイン境界に触れる変更。

## 番号の付け方

`001` から連番。**削除・欠番は気にしない**（履歴として残す）。
完了した spec も消さない — 「なぜこうしたか」の記録が本体。
