【生成ルール共通（品質基準）】

■ explanation（全体解説）— 120字以内
- 正解サービス・機能がなぜ要件を満たすかを核心のみ記述する
- 不正解との違いは choiceExplanations 側で説明する
- 先頭に「正解：」を書かない（UIが自動表示）
- 列挙・手順（①②③, ・, 1.2.3.）は1項目ごとに改行すること

■ 選択肢の文章量バランス（文字数から正解を推測させない）
- 各選択肢の文字数はできるだけ揃える（正解だけが突出して長い/短いのを避ける）
- 「正解は最長にならない」という規則性自体がメタ読みの手がかりになる。正解を最長から機械的に外さないこと。長さは正解・不正解と無相関にし、目安として4〜5問に1問程度（約20〜25%）は正解を最長の選択肢にしてよい
- 正解を「常に最長」または「常に非最長」に固定しない（長さと正解に相関を作らない）
- ただし正解が他の全選択肢より極端に長い（概ね1.5倍超、または正解だけ2文構成）のは長さだけで正解が分かる別の手がかりになるため避ける

■ ひっかけ強度・易しすぎ防止
- 問題文の決め手となる語を正解選択肢だけに出さない（全選択肢に分散させる）
- 不正解選択肢に「〜できない」等の自己否定文を書かない（理由はchoiceExplanationsへ）
- 正解選択肢の末尾に「〜なので要件を満たす」等の判定根拠を付けない
- 不正解選択肢を露骨な捨て選択肢（明らかに無関係・単一AZ等）にしない
- 定番の即答パターン（DAX/EFS/Multi-AZ等）はシナリオ化して複数要件を加える
- 正解に酷似した紛らわしい選択肢を最低1つ入れること（難易度向上）

■ 推敲・現行性
- 現行サービス名を使うこと（例: Amazon Data Firehose、旧Kinesis Data Firehoseは不可）
- CodeCommitは現行サービス（廃止扱い禁止）
- 実在しないサービス間の直接連携を前提にしない（中間サービスを省略しない）

■ isMultiple
- 正解が2つ以上の場合は isMultiple: true を必ず設定

■ choiceExplanations（選択肢別解説）
- choices と完全に同じ長さ・同じ順序で生成すること
- 各解説は上限80字（1文可）
- 文頭に必ずその選択肢のサービス名・機能名を主語として置くこと
  OK例: 「Amazon S3 は〜」「Lambda@Edge は〜」
  NG例: 「〜に対応していないため」「正しくは〜」「この構成では〜」
- 正解: なぜ正解か（根拠から書き始める）
- 不正解: なぜ不正解か（誤りの理由から書き始める）
- 文頭に「正解です」「不正解です」等の判定文を入れない

■ サービス特定キーワードの秘匿（易しすぎ防止）
- 問題文に正解サービスを一意に特定する固有語（Gremlin=Neptune、MongoDB互換=DocumentDB 等）や正解機能名（Warm Start 等）を書かない。要件は挙動・性質で記述する
- 正解選択肢に問題文の要件表現をほぼそのまま反復しない（「アーキテクチャを変更せず」→「リフト＆シフト」等の言い換え反復も不可）
- explanation・choiceExplanations の番号付き手順は必ず連番順（①②③④）で記述する

■ 不正解理由の事実正確性（choiceExplanations）
- 不正解の失格理由は「その要件を満たさない一点」に限定し事実正確に書く。機能の非対応・複雑さ・非ネイティブ等を一般論で断定しない（例: GitHub ActionsはEnvironmentのrequired reviewersで承認ゲートを標準サポート、TerraformのAWS対応は充実。これらを否定理由にしない）
- 問題文に正解を導く技術的根拠（数値上限・制約値・「〜が必要な理由」）を書かない。要件・症状のみ提示し、根拠の想起は受験者に委ねる（例: KMSの4KB上限を明記してエンベロープ暗号化へ誘導しない）
- 単一の用語区別・フェーズ配置（Annotations対Metadata、build対post_build等）を単体で問わず、複数要件・シナリオの中で取捨選択させる

■ 誤答の妥当性・選択肢参照の整合
- 不正解選択肢自体に虚偽の事実主張（「全て無料」「GitHub ActionsはDocker非対応」「OrganizationsではCloudTrail使用不可」等）を書かない。誤答も現実に選ばれうる妥当な構成とし、対象要件との不一致のみで不正解になるようにする（虚偽で消去法を成立させない）
- explanation・choiceExplanations 内で個別選択肢を「選択肢A/B/C/D」等のレターで参照しない。choices はUI上番号表示のため不一致になる。各選択肢の違いは対応する choiceExplanations に書く

■ 選択肢別解説の固有性
- choiceExplanations の各要素は他の選択肢と重複しない固有の内容にする（同一文の使い回し禁止）。各肢の正誤理由をその選択肢固有の観点で書き分けること

■ 論点の重複回避
- 決め手（正解の判定根拠）が同じ問題を、設定文言・シナリオを変えただけで複数作らない（例: 「MACsec=L2でDirect Connect専用接続のみ／IPsecはL3で不適」を別問で反復）。既出と結論・根拠が一致する問題は別サービス・別観点・別ドメインへ振り替える

■ 略語展開の一貫性（explanation・choiceExplanations）
- 略語（BLEU・ROUGE・BERT・AUC-ROC・RLHF 等）は初出で英語フルスペルを併記して展開する（例: MAE（Mean Absolute Error））
- 同一解説内で一部の略語だけ展開し他を未展開のまま残さない。使う略語はすべて同じ基準で展開する
